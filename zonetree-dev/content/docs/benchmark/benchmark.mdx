    <h2 id="benchmark-methodology-title">Methodology and reproduction</h2>
    <p>

      Read each result alongside its hardware, runtime, durability settings, and
      engine version. Linux and Windows runs can use different query limits and
      versions.

      <h3 id="benchmark-workload-title">Workload</h3>
      <p>
        Each engine stores the same profile records and maintains the same
        logical indexes:
      </p>
      <ul>
        <li>Individual profile inserts and updates.</li>
        <li>Primary-key reads and email lookups.</li>
        <li>
          Ordered index scans over country/status, creation time, and
          reputation.
        </li>
        <li>Indexed queries that also fetch matching profile records.</li>
        <li>Reads, lookups, scans, and queries after updates.</li>
        <li>
          Final settle or checkpoint, reopen, and persistence verification.
        </li>
      </ul>
      <p>
        Every measured phase contributes a deterministic checksum. Skipped work
        or incorrect results cannot count as a successful comparison.
      </p>
      <details class="zt-methodology-record">
        <summary>Profile data model</summary>

```csharp
UserProfile(
    UserId,
    Email,
    Country,
    Status,
    CreatedAtUnixMs,
    LastLoginUnixMs,
    Reputation,
    DisplayName,
    Bio)
```
      </details>
    </section>

    <section
      class="zt-methodology-card"
      aria-labelledby="benchmark-engine-layout-title"
    >
      <h3 id="benchmark-engine-layout-title">Engine layout</h3>
      <dl class="zt-methodology-definitions">
        <div>
          <dt>ZoneTree</dt>
          <dd>
            Separate ZoneTree instances hold the primary records and
            application-managed secondary indexes.
          </dd>
        </div>
        <div>
          <dt>RocksDB</dt>
          <dd>
            Separate databases hold records and indexes. Separate writes, rather
            than a <code>WriteBatch</code>, mirror the ZoneTree layout.
          </dd>
        </div>
        <div>
          <dt>SQLite and MySQL</dt>
          <dd>
            A profile table uses native SQL indexes, maintained inside the
            database engine.
          </dd>
        </div>
      </dl>
      <p class="zt-methodology-note">
        MySQL is a client/server baseline measured over TCP. Its server or
        container memory is excluded from the reported client-process memory.
      </p>
    </section>

  <section

    aria-labelledby="benchmark-reading-title"
  >
    <h3 id="benchmark-reading-title">Reading the reports</h3>
    <dl class="zt-methodology-definitions zt-methodology-metrics">
      <div>
        <dt>Completed phase time</dt>
        <dd>
          The sum of measured workload phases. Excludes initialization,
          stabilization, settle or checkpoint, reopen, verification, and report
          writing.
        </dd>
      </div>
      <div>
        <dt>Full run time</dt>
        <dd>
          The complete engine run, including work outside the measured phases.
        </dd>
      </div>
      <div>
        <dt>Stabilization</dt>
        <dd>
          ZoneTree and RocksDB settle or compact after inserts and updates,
          before read/query measurements. This reduces background-maintenance
          noise.
        </dd>
      </div>
      <div>
        <dt>Storage</dt>
        <dd>Disk usage after the engine settles or checkpoints its data.</dd>
      </div>
      <div>
        <dt>Process peak memory</dt>
        <dd>
          A high-water mark for the benchmark process. Includes embedded
          engines, but excludes the MySQL server. It is not steady-state memory
          usage.
        </dd>
      </div>
      <div>
        <dt>Scan vs. query throughput</dt>
        <dd>
          Index scans read index records only. Queries also fetch the matching
          profile records.
        </dd>
      </div>
    </dl>
  </section>

  >
    <h3 id="benchmark-reproduce-title">Reproduce the benchmark</h3>
    <p>
      Run from <code>benchmarks/profile-store</code> with the .NET SDK and
      sufficient disk space. Reference runs disable tiered compilation;
      first-use JIT work inside a measured phase still counts.
    </p>

```bash
export DOTNET_TieredCompilation=0
dotnet run --project src/ProfileStore.Benchmark.csproj -c Release -- \
  --engine zonetree,rocksdb,sqlite \
  --profiles 100K,500K,1M,2M,5M,10M \
  --parallelism 1,16 \
  --output results --data data --update-latest \
  --timeout-seconds 1200
```

    <p class="zt-methodology-note">
      In PowerShell, set <code>$env:DOTNET_TieredCompilation = "0"</code> and
      put the <code>dotnet run</code> command on one line, without the Bash
      continuation characters.
    </p>
    <p>
      For MySQL, use the benchmark Docker setup or a separately configured
      server. The
      <a
        href="https://github.com/ZoneTree/ZoneTree/blob/main/benchmarks/profile-store/README.md"
        >benchmark README</a>
      covers Docker commands, prerequisites, runtime policy, and cleanup.
    </p>
  </section>

  <section class="zt-methodology-card" aria-labelledby="benchmark-scope-title">
    <h3 id="benchmark-scope-title">Tradeoffs and scope</h3>
    <p>
      This workload is useful for applications with live individual writes,
      ordered keys, range scans, secondary indexes, and profile-style values.
      Compare completed runs on the same documented machine.
    </p>
    <p>
      Read throughput and storage together with memory. ZoneTree can cache
      decompressed disk blocks during reads and scans; cache lifetime controls
      when unused blocks are released. The .NET runtime can retain that memory
      for reuse after release.
    </p>
    <p>
      Results depend on CPU, storage, operating system, runtime, compression,
      background activity, and query distribution. For different record sizes,
      write batching, transaction boundaries, durability requirements, or
      deployment models, rerun with your target workload and hardware.
    </p>
  </section>
