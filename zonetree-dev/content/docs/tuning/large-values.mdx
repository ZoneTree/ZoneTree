## Payload storage models

| Model | Useful when | Responsibility to account for |
| --- | --- | --- |
| Store the payload directly | Reads and updates usually consume the whole value. | The full value participates in logging, serialization, disk reads, and changed-range merges. |
| Store metadata and a content reference | Queries mostly filter or order small metadata, or payloads have a separate delivery path. | Coordinate the payload store, reference publication, and cleanup. ZoneTree does not make updates across external stores atomic. |
| Split independently accessed data into records | Fields or chunks have different access and update patterns. | Design key ordering and application consistency across those records. |

Direct strings and `Memory<byte>` values use built-in serializers. `byte[]` is not a supported key/value type; wrap owned bytes in `Memory<byte>`. Custom document types need a compatible serializer. Keep stored objects and backing buffers read-only; see [value ownership](../concepts/value-mutability.mdx).

## Translate counts before choosing a limit

For a 128 KiB average payload, these counts already imply substantial data before keys, indexes, object overhead, and compression:

```text
10,000 records  × 128 KiB ≈ 1.22 GiB of payload
100,000 records × 128 KiB ≈ 12.2 GiB of payload
```

For mutable capacity, estimate retained object and buffer size. For disk-part targets, estimate serialized bytes and measured compression. Include simultaneously frozen segments and active merge buffers in addition to the mutable set; [memory usage](../storage/memory-usage.mdx) describes those owners.

Reducing `MutableSegmentMaxItemCount` rotates the active set sooner. It does not cap total process memory or resolve a merge backlog. Smaller batches may increase merge frequency, so watch `ReadOnlySegmentsRecordCount` and sustained merge throughput while changing it.

## Exercise the actual payload representation

This complete example stores owned 128 KiB byte buffers with a lower mutable capacity, finishes a controlled merge, and reads a value back. The generated bytes exercise the storage path; use your actual payload distribution for performance measurements.

```csharp
using ZoneTree;

var directory = Path.Combine("data", "large-payloads", Guid.NewGuid().ToString("N"));
using var tree = new ZoneTreeFactory<int, Memory<byte>>()
    .SetDataDirectory(directory)
    .SetMutableSegmentMaxItemCount(1000)
    .Create();
using var maintainer = tree.CreateMaintainer();
var random = new Random(42);

for (var key = 0; key < 32; ++key)
{
    var bytes = new byte[128 * 1024];
    random.NextBytes(bytes);
    tree.Upsert(key, bytes.AsMemory());
    // The tree retains this view; leave its backing buffer unchanged.
}

maintainer.EvictToDisk();
await maintainer.WaitForBackgroundThreadsAsync();

if (!tree.TryGet(7, out var value) || value.Length != 128 * 1024)
    throw new InvalidOperationException("Expected the complete payload.");

Console.WriteLine($"Read {value.Length} bytes.");
```

The capacity is a record threshold; this program does not need to fill it before merging. It keeps the default AsyncCompressed WAL and disk compression.

## Isolate the payload-specific pressure

| Observation | Experiment | Check alongside the result |
| --- | --- | --- |
| Active write memory is too large | Reduce mutable capacity using retained bytes per record. | Frozen records, merge frequency, and peak memory. |
| Local merges rewrite too many payload bytes | Reduce multipart targets using serialized bytes per record. | Part count and reuse; broad random updates may still touch most parts. |
| Samples retain large deserialized values | Increase the sparse-index step or compare disabling the default index. | Point-read search cost. Sparse entries include values. |
| Batched reads retain too many payload objects | Reduce `MaterializedEntryCacheSize`, or compare `0`. | Deserialization and allocation rate on repeated reads. |
| Repeated point reads retain large values | Reduce `ValueCacheSize` or its retention setting. | Repeat-read latency and decoding work. |
| Compression spends CPU with little size reduction | Compare codecs with `CompressionMethod.None` using the same payload bytes. | WAL and disk profiles separately, storage traffic, and latency. |

Use [disk segment tuning](disk-segments.mdx) for valid part targets and [read-path caching](read-path-caching.mdx) for cache scopes and cleanup behavior.

## Measure full-value reads and scans

Smaller disk blocks can reduce unrelated neighboring data read for a point lookup. They cannot avoid reading and decoding the requested value itself; a large value may span several blocks and require intermediate buffers.

Iterator prefetch can also materialize multiple large values at once. For short or early-terminated scans, compare it with prefetch disabled. Leave block-cache contribution off for one-off scans unless measured reuse justifies retaining their blocks. Include sparse samples, materialized values, and per-thread search hints in the read-memory budget.

If most queries only need metadata, a separate compact index can keep those queries on small values and fetch external content only for selected results. Coordinate reference and content lifetimes so readers can resolve the referenced payload throughout their operation.
