## Why a read and a write need a lock

Every ZoneTree call is safe to make from many threads, but two calls are not one step. When two threads increment the same counter at the same time, both can read `5`, both write `6`, and one increment is lost:

```csharp
// Two threads can run these lines at the same time.
tree.TryGet(key, out var count);
tree.Upsert(key, count + 1);
```

A key lock turns the read and the write into one step for every caller that takes the lock.

## Count from many threads

This complete console program increments one counter from eight threads, 1,000 times each. Run it in a console project with the `ZoneTree` package installed:

```csharp
using ZoneTree;

using var tree = new ZoneTreeFactory<string, long>()
    .SetDataDirectory("data/key-lock-example")
    .OpenOrCreate();
using var maintainer = tree.CreateMaintainer();

var key = "page:home:views";
// Start from zero, so every run prints the same total.
tree.Upsert(key, 0);

Parallel.For(0, 8, _ =>
{
    for (var i = 0; i < 1000; ++i)
    {
        using (tree.Lock(key))
        {
            tree.TryGet(key, out var views);
            tree.Upsert(key, views + 1);
        }
    }
});

tree.TryGet(key, out var total);
Console.WriteLine($"Views: {total}");
```

It prints `Views: 8000`. Without the `using (tree.Lock(key))` line, most increments are lost: the threads overwrite each other's writes, and the total comes out far below 8000.

`tree.Lock(key)` returns a scope that holds the lock until it is disposed, so the `using` statement releases the lock even when the code inside throws. When the key is absent, `TryGet` sets `views` to `0`, so the same code also starts a new counter. Maintenance can move and merge data in the background while you hold the lock. That never changes the key's newest value, so the read and the write stay correct.

## Choose a call

| Call | Use it to |
| --- | --- |
| `using (tree.Lock(key))` | Lock one key, waiting until it is free. |
| `using (tree.LockMany(key1, key2))` | Lock several keys at once, without deadlocks. |
| `tree.TryLock(key, timeout, out var scope)` | Give up when the key stays locked for longer than the timeout. |
| `using (await tree.LockAsync(key, cancellationToken))` | Wait without blocking the thread, and await inside the lock. |
| `using (await tree.LockManyAsync([key1, key2], cancellationToken))` | Lock several keys asynchronously. |

Each call returns a scope that releases its locks when it is disposed. Dispose it exactly once, with a `using` statement.

## Replace a value only when it matches

This method advances a job's revision only when the stored revision is the one the caller expects, so two workers cannot both advance it from the same revision:

```csharp
bool TryAdvanceRevision(string job, long expected)
{
    var key = $"job:{job}:revision";
    using (tree.Lock(key))
    {
        if (!tree.TryGet(key, out var revision) || revision != expected)
            return false;
        tree.Upsert(key, expected + 1);
        return true;
    }
}
```

## Claim a key once

`TryAdd` checks that the key is absent and then writes it, in two steps. Under the key lock, only one of several callers that claim the same name succeeds:

```csharp
bool TryClaimUserName(string userName, long userId)
{
    var key = $"username:{userName}";
    using (tree.Lock(key))
        return tree.TryAdd(key, userId, out _);
}
```

## Lock several keys

Locking two keys one after the other can deadlock: one caller locks `a` and waits for `b`, while another locks `b` and waits for `a`. Lock them with one `LockMany` call instead. It takes the locks in a fixed order, so callers that name the same keys in a different order do not deadlock:

```csharp
bool TryTransfer(string from, string to, long amount)
{
    using (tree.LockMany(from, to))
    {
        tree.TryGet(from, out var fromBalance);
        if (fromBalance < amount)
            return false;
        tree.Upsert(from, fromBalance - amount);
        tree.TryGet(to, out var toBalance);
        tree.Upsert(to, toBalance + amount);
        return true;
    }
}
```

The lock keeps other writers out while the method runs, but the two writes are still two writes: a crash between them can keep one and lose the other. When keys must change together or not at all, use a [transaction](transactions.mdx).

## Wait asynchronously

`LockAsync` waits for the key without blocking the thread, and the code inside the lock can await. Synchronous and asynchronous callers of the same key exclude each other. This method reserves stock and records the reservation in another service while it holds the lock:

```csharp
async Task<bool> TryReserveAsync(string sku, long quantity, CancellationToken cancellationToken)
{
    var key = $"stock:{sku}";
    using (await tree.LockAsync(key, cancellationToken))
    {
        if (!tree.TryGet(key, out var stock) || stock < quantity)
            return false;
        await reservations.RecordAsync(sku, quantity, cancellationToken);
        tree.Upsert(key, stock - quantity);
        return true;
    }
}
```

A cancelled wait throws `OperationCanceledException` and holds nothing. `LockManyAsync` locks several keys the same way:

```csharp
using (await tree.LockManyAsync([from, to], cancellationToken))
{
    // Both keys are locked.
}
```

Take the lock with `LockAsync` or `LockManyAsync` whenever the code inside awaits. A lock from `Lock` or `TryLock` belongs to the thread that took it: while the code awaits, that thread runs other work, which gets a `LockRecursionException` if it locks the same key.

## Give up after a timeout

`TryLock` waits up to the timeout and returns `false` if the key is still locked. Then it holds nothing:

```csharp
bool TryIncrement(string key)
{
    if (!tree.TryLock(key, TimeSpan.FromMilliseconds(100), out var scope))
        return false; // The key stayed busy. Try again later.
    using (scope)
    {
        tree.TryGet(key, out var count);
        tree.Upsert(key, count + 1);
        return true;
    }
}
```

A zero timeout does not wait at all, and `Timeout.InfiniteTimeSpan` waits until the key is free.

## How keys share locks

A tree has a fixed number of locks, set by `LockStripeCount`: 1,024 by default. Each key takes one of them, chosen by the [key hasher](../concepts/key-ordering.mdx). Keys that the comparer considers equal always take the same lock, such as `"a"` and `"A"` under a case-insensitive comparer.

Two different keys can also take the same lock. Then they wait for each other, which is still correct but slower. More locks make that rarer, for a little memory:

| `LockStripeCount` | Chance that two keys share a lock | Memory once keys are locked |
| --- | --- | --- |
| `1` | Always: one lock for every key. | One lock. |
| `1024` (default) | 1 in 1,024. | About 64 KB. |
| `16384` | 1 in 16,384. | About 1 MB. |

The value is rounded up to a power of two. A tree that never locks a key uses no memory for locks.

```csharp
using var tree = new ZoneTreeFactory<string, long>()
    .SetDataDirectory("data/key-lock-example")
    .Configure(options => options.LockStripeCount = 16384)
    .OpenOrCreate();
```

Common key types have a key hasher built in. A custom key type needs a hasher that gives keys the comparer considers equal the same hash, as in [implementing a custom key type](../concepts/key-ordering.mdx#implement-a-custom-key-type), or a `LockStripeCount` of `1`. Opening the tree tells you when the hasher is missing, and for string keys it refuses a hasher that tells apart keys the comparer considers equal. Beyond that, ZoneTree cannot check your hasher: if it disagrees with the comparer, equal keys can take different locks and do not wait for each other.

## Rules

- **The lock is not reentrant.** While a thread holds a key's lock, locking that key again, or a key that shares its lock, throws `LockRecursionException`. Code that holds a lock from `LockAsync` and locks the key again waits forever instead. Lock all the keys you need with one `LockMany` call.
- **Await only inside an asynchronous lock.** Use `LockAsync` or `LockManyAsync` when the code inside the lock awaits.
- **Keep the locked section short.** Other writers of the key, and of keys that share its lock, wait for it.
- **Dispose each scope once.** Disposing it twice releases a lock that another caller may hold by then.
- **Write the new value.** Changing a stored object in place is not a write. Build a replacement and write it with `Upsert`. See [value mutability](../concepts/value-mutability.mdx).
- **The locks live in memory, in one tree object.** They do not coordinate other processes or other trees, and they are not saved with the data.
- **A null key locks like any other key.** A null array or list of keys throws `ArgumentNullException`.

## Cost

A key lock costs about as much as a `lock` statement, and much less than a `SemaphoreSlim` when callers wait asynchronously. Measured with .NET 11:

| Lock | One thread | 8 threads on one key | Allocation |
| --- | --- | --- | --- |
| `lock` statement | ~16 ns | ~100 ns | none |
| `tree.Lock(key)` | ~13 ns | ~86 ns | none |
| `await semaphore.WaitAsync()` | ~32 ns | ~595 ns | 192 B per contended wait |
| `await tree.LockAsync(key)` | ~24 ns | ~105 ns | none |

One thread: taking and releasing a free lock. 8 threads: the time per increment when 8 threads increment one key, with `TryGet` and `Upsert` inside the lock.
