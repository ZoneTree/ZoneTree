## Commit related writes

This complete console example moves an amount between two accounts. It reads both balances inside the transaction, writes both, and retries the whole unit of work when the commit conflicts:

```csharp
using ZoneTree;
using ZoneTree.Exceptions;

using var tree = new ZoneTreeFactory<string, long>()
    .SetDataDirectory("data/transactions-example")
    .OpenOrCreateTransactional();
using var maintainer = tree.CreateMaintainer();

bool Transfer(string from, string to, long amount)
{
    for (var attempt = 0; attempt < 10; ++attempt)
    {
        try
        {
            using var tx = tree.BeginTransaction();
            tx.TryGet(from, out var fromBalance);
            tx.TryGet(to, out var toBalance);
            if (fromBalance < amount)
                return false;
            tx.Upsert(from, fromBalance - amount);
            tx.Upsert(to, toBalance + amount);
            if (tx.TryCommit())
                return true;
        }
        catch (TransactionConflictException)
        {
            // A write conflicted before the commit. The transaction is rolled back.
        }
    }
    throw new TimeoutException("The transfer kept conflicting.");
}
```

`BeginTransaction()` returns an `ITransaction<TKey, TValue>`. Reads and writes go through the transaction, and disposing a transaction that has not committed rolls it back.

## Single-key and multi-key coordination

| Data rule | API |
| --- | --- |
| Replace a value without reading its previous state. | [Ordinary writes](reads-and-writes.mdx). |
| Compute one key's new value from its current value. | [Atomic operations](atomic-operations.mdx). |
| Read or change several related keys as one transaction. | Transactional tree. |

Concurrent application threads alone do not require transactions. Use them for a multi-key invariant, and make the reads that decide the writes part of that transaction.

## How a transaction works

1. `BeginTransaction()` takes a snapshot: the transaction reads the database as of the latest commit, plus its own writes.
2. Writes are stored at once, tagged with the transaction, and stay invisible to other transactions.
3. `Commit()` or `TryCommit()` checks for conflicts with transactions that committed after the snapshot. Without a conflict, a single commit record makes every write visible together.
4. On a conflict, or after `Rollback()`, the writes are discarded and the transaction ends.

Reads never block, and nothing locks a key. Concurrent transactions only meet at commit time: the transaction that commits first wins, and the other one fails and must be retried from its first read.

| Outcome | How it is reported | What the caller does |
| --- | --- | --- |
| Committed | `Commit()` returns; `TryCommit()` returns true. | Continue with work that depends on success. |
| Conflict at commit | `Commit()` throws `TransactionConflictException`; `TryCommit()` returns false. | Retry the whole unit of work. |
| Conflict while writing | `Upsert` and `Delete` throw `TransactionConflictException` when the key was already committed by a newer transaction. | Retry the whole unit of work. |
| Rolled back | `Rollback()` or `Dispose()` before the commit. | Nothing; the writes never become visible. |

After any of these outcomes the transaction cannot be used again. Start a new one for the retry, and read the current values again inside it.

## Choose an isolation level

`BeginTransaction` takes an isolation level. Both levels read a consistent snapshot and never lose a concurrent write to the same key.

| Level | A commit fails when a newer commit wrote... | Allows |
| --- | --- | --- |
| `Serializable` (default) | a key this transaction wrote, a key it read, or any key inside a range it iterated, including keys that did not exist before. | Nothing: committed transactions behave as if they ran one at a time, in commit order. |
| `Snapshot` | a key this transaction wrote. | Write skew: two transactions each read what the other one changes, and both commit. |

Use `Serializable` unless profiling shows that its read tracking matters. It keeps the keys a transaction read and the ranges it iterated until the commit, so a transaction that reads millions of keys holds that read set in memory. `Snapshot` keeps only the written keys and conflicts less often.

## Read ranges

Transaction iterators read the same snapshot as point reads, in ascending or descending key order:

```csharp
using var tx = tree.BeginTransaction();
using var iterator = tx.CreateIterator();
iterator.Seek("order:");
while (iterator.Next() && iterator.CurrentKey.StartsWith("order:"))
    Console.WriteLine($"{iterator.CurrentKey} = {iterator.CurrentValue}");
```

In a serializable transaction, an iterator adds the range from its seek key to the last key it read to the read set. A commit after the snapshot that writes inside that range, even a brand new key, makes this transaction conflict. Stop iterating when you have what you need: an iterator that runs to the end protects the rest of the key space too.

An iterator sees the transaction's own writes made before each `Seek`, `SeekFirst`, or first `Next` call. Dispose iterators when the scan is done; they cannot be used after the transaction ends.

## Read-only transactions

`BeginReadOnlyTransaction()` reads a consistent snapshot without a transaction id or a read set. It never conflicts, and its commit only ends it. Use it for reports, exports, and any query that must see several keys or ranges at one point in time.

```csharp
using var snapshot = tree.BeginReadOnlyTransaction();
var total = 0L;
using var iterator = snapshot.CreateIterator();
while (iterator.Next())
    total += iterator.CurrentValue;
```

A long-running snapshot keeps the versions it can read: merges cannot drop a version that an open transaction may still read. End transactions when their work is done.

## Durability

A committed transaction is visible at once but is durable only after the write ahead log syncs. Choose how commits reach the disk:

| Need | API |
| --- | --- |
| This commit must survive a power loss before you acknowledge it. | `await tx.CommitDurableAsync()` |
| Several commits must be durable; acknowledge them together. | Commit each, then `await tree.SyncWALAsync()` once. |
| Bound how much a power loss can lose without waiting on syncs. | `tree.AutoSyncInterval = TimeSpan.FromMilliseconds(10)` |

Concurrent `CommitDurableAsync` and `SyncWALAsync` callers share disk syncs, so many committing threads pay for one sync together. A single thread that waits after every commit pays a full sync per commit.

A crash never recovers part of a transaction. After a restart the tree contains a prefix of the committed transactions in commit order; transactions that had not committed are rolled back while the tree opens. See [WAL modes](../durability/wal-modes.mdx) for how each mode trades write speed for the commits a crash can lose.

## Transaction size

A transaction's writes are stored in the tree as it makes them, so they persist, move to disk, and merge like other records. Its size is limited by the disk, not the memory. The memory holds only the keys it wrote and, in serializable mode, the keys and ranges it read.

Rolling back a large transaction writes a deletion for every key it wrote, and merges remove its versions over time.

## Maintenance

A maintainer merges the storage tree in the background, and merges also drop the versions no open transaction can read. Keep one running with the tree.

| Surface | Purpose |
| --- | --- |
| `tree.CreateMaintainer()` | Background merges and version cleanup. |
| `tree.Maintenance.ZoneTree` | The storage tree. Every key is stored with the id of the transaction that wrote it. Do not write to it directly. |
| `tree.Maintenance.ActiveTransactionCount` | Transactions that have not ended. A count that keeps growing usually means transactions are not disposed. |
| `tree.Maintenance.AbortedTransactionCount` | Rolled back transactions whose versions may still be stored. |
| `tree.Maintenance.ConflictIndexCount` | Recently committed keys kept to detect conflicts with older transactions. |
